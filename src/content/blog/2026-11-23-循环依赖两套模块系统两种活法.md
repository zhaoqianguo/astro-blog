我写前端的那几年，一直觉得 `import` 和 `require` 就是同一件事换了层语法。类型检查跑通，单测全绿，模块引用能有什么问题。

后来在一台服务器上被打脸。本地一切正常，某次只是挪了一行工具函数的引用位置，上线之后页面一加载就抛 `ReferenceError: Cannot access 'X' before initialization`。另一次更难受，同一个公共库被两个子依赖分别引了进来，运行时做 `instanceof` 判断返回了 false，全局鉴权上下文莫名其妙就丢了。

TypeScript 在这两件事上一句话都说不出来。在类型系统眼里每个导出都合法，可引擎底下跑的是两套完全不同的规矩。

这篇的骨架来自《深入解析 JavaScript 循环依赖与模块副作用》，原文发在 51Testing，作者没有署名，地址放在最后。它给的七段代码我都在 `node v22.22.1` 下重跑了一遍，下面出现的输出都是我这边打出来的。

## 两段看起来等价的代码

先看最朴素的状态共享。ESM 里导出一个变量和一个修改方法：

```js
// state.mjs
export let status = "starting";
export function start() {
  status = "ready";
}
```

业务代码引进去，调一下：

```js
import { status, start } from "./state.mjs";
console.log("调用前 status =", status);
start();
console.log("调用后 status =", status);
```

跑出来是 `starting` 然后 `ready`，符合直觉。

把同样的东西写成 CommonJS，然后习惯性地解构引入：

```js
// state.cjs
module.exports.status = "starting";
module.exports.start = function () {
  module.exports.status = "ready";
};
```

```js
const { status, start } = require("./state.cjs");
console.log("调用前 status =", status);
start();
console.log("调用后 status =", status);
```

两行都打 `starting`。可 `start()` 明明把 `module.exports.status` 改成了 `ready`。

不去解构、保留整个对象，就正常了：

```js
const state = require("./state.cjs");
console.log("调用前 =", state.status);
state.start();
console.log("调用后 =", state.status);
```

三段并排跑，输出是这样：

```
node v22.22.1
ESM 调用前 status = starting
ESM 调用后 status = ready
CJS 解构 调用前 status = starting
CJS 解构 调用后 status = starting
CJS 整对象 调用前 status = starting
CJS 整对象 调用后 status = ready
```

这不是 bug，是两份不同的契约。ESM 的具名导入建的是一个只读活绑定，导入方的变量名直接映射到导出模块内部的词法槽位上，导出方一赋值，读的人立刻看到新值。CommonJS 的 `require()` 返回的就是个普通对象，`const { status }` 是标准解构，把那个瞬间的属性值拷进了局部变量。从那一刻起它就与原来的对象无关了。

从 CJS 往 ESM 迁移时「状态死活不同步」，根子都在这。

## 静态图链接和运行时求值

变量怎么绑定是一层差异，代码什么时候执行是另一层。

ESM 的静态导入参与整棵依赖图的构建。入口文件第一行可执行代码开跑之前，引擎必须把所有依赖解析完、实例化完、绑定关系连好。所以 `import` 写在文件哪个位置都不影响执行顺序：

```js
// app.mjs
console.log("app: import 之前");
import "./setup.mjs";
console.log("app: import 之后");
```

```js
// setup.mjs
console.log("setup 的顶层代码执行了");
```

跑出来是 `setup` 先说话，然后才是入口文件的第一行。我把 `import` 挪到文件末尾试过，结果一样。

`require()` 就老实多了，它是个普通的同步函数调用，执行指针走到那一行才去读文件、跑代码、把 `module.exports` 塞进 `require.cache`：

```
--- 静态导入 ---
setup 的顶层代码执行了
app: import 之前
app: import 之后
--- require ---
app: require 之前
setup.cjs 的顶层代码执行了
app: require 之后
```

这些词平时被叫成「导入提升」，听着像语法层面的代码置顶。它不是。它是两阶段生命周期在起作用，引擎先深度优先遍历整张图，再按拓扑顺序求值。

这个顺序差异有个很常见的翻车点。入口文件第一行写 `process.env.PORT = '8080'`，第二行静态导入数据库模块，然后发现数据库模块读到的还是 `undefined`：

```js
// env.mjs
process.env.PORT = "8080";
import "./db.mjs";
console.log("入口赋值之后 PORT =", process.env.PORT);
```

```
db 模块读到的 PORT = undefined
入口赋值之后 PORT = 8080
```

`db.mjs` 在那个 `= '8080'` 被执行之前就已经跑完了。真要让配置先生效，得换成动态 `import()`，它是个运行时表达式，返回 Promise，走到才拉取。

## 循环里的两种事故现场

A 引 B、B 又引 A 的时候，两套机制的应对方式差得最远。

CommonJS 为了不死循环，策略是「先交半成品」。检测到目标模块正在加载中，就把当前挂在 `exports` 上的对象直接递过去：

```js
// a.cjs
console.log("a: 开始执行");
exports.ready = false;
const b = require("./b.cjs");
console.log("a: 读取 b.ready =", b.ready);
exports.ready = true;
console.log("a: 执行完毕");
```

```js
// b.cjs
console.log("b: 开始执行");
const a = require("./a.cjs");
console.log("b: 读取 a.ready =", a.ready);
exports.ready = true;
console.log("b: 执行完毕");
```

```
a: 开始执行
b: 开始执行
b: 读取 a.ready = false
b: 执行完毕
a: 读取 b.ready = true
a: 执行完毕
```

`b` 那一行读到的 `false` 就是半成品的味道：`a` 只挂了个 `ready: false` 出去，`ready = true` 还没轮到。

真正要命的是那些「在 require 之后才导出」的东西。我把 `a.cjs` 里那个 `exports.late` 挪到 `require('./b.cjs')` 后面，`b` 那边拿到的是 `undefined`，同时 Node 打了条警告：

```
f: typeof e.late = undefined
(node:48454) Warning: Accessing non-existent property 'late' of module exports inside circular dependency
```

而同一次实验里，如果 `helper` 是在 `require` 之前挂上去的，对面就能正常拿到函数（`typeof c.helper = function`）。同一个文件里两行导出，一行能到、一行到不了，区别只在先后。这种静默缺一半的状态，往往要跑到很久以后某个空指针调用才暴露。

ESM 这边不给你缓冲。变量声明走严格词法作用域，循环依赖撞上就是当场报错：

```js
// a.mjs
import { b } from "./b.mjs";
export const a = "a";
console.log("a: b =", b);
```

```js
// b.mjs
import { a } from "./a.mjs";
console.log("b: a =", a);
export const b = "b";
```

```
ReferenceError: Cannot access 'a' before initialization
    at file:///private/tmp/mod4/b.mjs:2:23
    at ModuleJob.run (node:internal/modules/esm/module_job:343:25)
```

原因很干净：链接阶段确实已经给 `a` 分配了绑定槽位，但按拓扑顺序先跑的是 `b.mjs`，`a.mjs` 里那句 `export const a = 'a'` 还没执行。此刻 `a` 在暂存死区里，碰一下就是 `ReferenceError`。

我见过有人顺手包一个 `setTimeout` 绕过去：

```js
setTimeout(() => console.log("b: 延迟读 a =", a), 0);
```

它能跑，输出是 `b: 延迟读 a = a`。但这只是把稳定性押在执行时序的巧合上。别人改一处 import，加载顺序一变，异常立刻回来。

## 跨边界的双包灾难

单套系统内部的事还算好理解。真正难查的是两套混着用。

现在很多库为了兼顾老代码的 `require` 和新项目的 `import`，会在 `package.json` 里配条件导出，同一份源码编出两份产物：ESM 一份 `.js`，CJS 一份 `.cjs`。我在 `/tmp` 里伪造了这么一个包，两份产物里各写一个 `Token` 类，源码逐字相同：

```js
import { createRequire } from "node:module";
import { Token as ImportedToken } from "auth-sdk";
const require = createRequire(import.meta.url);
const { Token: RequiredToken } = require("auth-sdk");

const token = new ImportedToken("secret-123");
console.log("token instanceof ImportedToken =", token instanceof ImportedToken);
console.log("token instanceof RequiredToken =", token instanceof RequiredToken);
```

```
token instanceof ImportedToken = true
token instanceof RequiredToken = false
两个 Token 相等吗 = false
```

代码一模一样，`instanceof` 一个 true 一个 false。因为在加载器眼里 `./dist/index.js` 和 `./dist/index.cjs` 是两个不同路径的文件，各自独立加载，各自生成互不相通的缓存。它们导出的 `Token` 是两个不同的构造函数，原型链都是分开的。

我顺手查了一下缓存，想看看是不是真的存了两份：

```
require.cache 里 auth-sdk 的条目: 1
  /private/tmp/mod6/node_modules/auth-sdk/dist/index.cjs
```

只看到一条。ESM 那份不在 `require.cache` 里，它有自己的一套模块表，两套缓存不共享。这个细节比原文说的「两份互不相通的缓存」更准确一点：不是同一张表里存了两行，而是两张表各存一行。

这个问题的破坏力取决于库里存了什么。要是留着数据库连接池、全局事件总线、用户 Session 单例，同一个进程里就真有两套状态在跑，一边改了登录凭证，另一边浑然不知。Webpack 或 Vite 全量打包时有时会被去重策略盖过去，走 Node 原生服务端就几乎百分之百撞上。

## 我现在怎么防

这些坑没法靠业务代码里到处打补丁解决，得在依赖形状和发包流程上挡。

第一件事是把共享逻辑下沉。A 和 B 互相引对方的常量、类型、小工具函数时，通常说明中间少了一层。把被公用的部分抽到 `types.ts`、`constants.ts` 这种叶子模块里，两边单向依赖它，环就断了。如果 A 真需要 B 的运行时实例，用参数或者依赖注入在运行时传进去，别在文件顶层把引用写死。

第二件事是管住模块顶层的副作用。顶层别直接发网络请求、读还没注入的环境变量、改全局对象。确实需要异步初始化的东西，显式导出一个 `initClient()` 或者一个 Promise，让业务层在明确的启动生命周期里 await 它，把控制权还回去，而不是赌加载顺序。

第三件事是发公共库之前用 `npm pack` 做真实安装烟测。源码目录里单测全绿不够。打个 `.tgz`，扔进干净的临时工程里装上，分别写一个 `.mjs` 和一个 `.cjs` 脚本跑最基础的引入，确认 `import` 和 `require` 拿到的 API 一致、类没分裂、单例没变两份。我上周给一个内部包补这一步的时候，第一次跑就查出 `exports` 字段漏配了 `require` 分支，CJS 侧一直在拿默认导出。

这七段代码前后跑了大概一小时，最有用的不是哪一条结论，是那个 `require.cache` 只有一条的输出。它让我意识到所谓「两套系统」不是抽象的比喻，它们在进程里真的各有一套自己的账本。
